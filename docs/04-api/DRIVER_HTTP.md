## 1. ماذا أُضيف

`createDriverApp({ runner, health?, tickState?, logger? })` مصنع Fastify لثلاثة عشر مساراً و`/health`، ولا يبدأ الاستماع. جذر التركيب في `server.ts` يختار `PostgresDriverRunner` عند وجود `DATABASE_URL`، وإلّا يركّب بيئة ذاكرة ويُعلن `degraded` في `/health` بدل أن يتظاهر بالسلامة.

```text
services/drivers/src/http/requests.ts        ← الترويسات، معرّف WS-، UUID، رفض المفاتيح الزائدة، قرّاء الأشكال
services/drivers/src/http/idempotency.ts     ← مفتاح مُنطَّق + بصمة sha256 للحمولة → "fresh" | "replay"
services/drivers/src/http/errors.ts          ← DriverError أو فشل النقل → { error:{code,message,details?}, trace_id }
services/drivers/src/http/app.ts             ← المسارات الثلاثة عشر + /health + tickState
services/drivers/src/use-cases/read-driver.ts← القراءات الأربع: الملف والمناطق والمركبات والوثائق
services/drivers/src/http/server.ts          ← composition root (Postgres أو ذاكرة) + SIGTERM/SIGINT
```

**لم نعدّل أيّ ملف كتابة في `src/use-cases/` ضمن هذه المهمة.** ما أُضيف هناك ملف قراءة واحد لأنّ المستودعات ترجع `[]` للسائق المجهول، وقائمة فارغة ليست جواباً صحيحاً عن سؤال «هل هذا السائق موجود؟» — §4.

### 1.1 لماذا لا يستقبل التطبيق التبعيات مباشرة

يستقبل `createDriverApp` **مقبس معاملة واحداً** (`DriverRunner {write, read}`) لا خريطة مستودعات. معالج HTTP لا يفتح معاملة بنفسه ولا يعرف أنّ هناك Postgres؛ يبني مدخلات حالة الاستخدام من الطلب ويسلّمها إلى `runner.write` أو `runner.read`. لهذا صار حقن Runner فاشل في اختبار الأخطاء (§8) ممكناً بثلاثة أسطر.

## 3. منع التكرار عند الحدّ

### 3.1 `POST /drivers`: المسؤولية عند HTTP

`registerDriver` لا يأخذ مفتاح منع تكرار، ولا أضفناه إليه. المفتاح يُحسم في `app.ts` داخل **معاملة `runner.write` واحدة**:

1. `registrationKey(waslaPublicId, key)` → `profile:<id>:<key>` — التنطيق يمنع تصادم مفتاح تسجيل مع مفتاح مركبة أو وثيقة للمخزن نفسه.
2. `payloadFingerprint(body)` → sha256 لصورة قانونية مرتّبة المفاتيح. **لا يُخزَّن اسم السائق قابلاً للقراءة** في سجلّ منع التكرار؛ يُخزَّن هضمه.
3. `classifyReplay` يعيد `"replay"` عند تطابق البصمة، ويرفع `DRIVER_IDEMPOTENCY_KEY_REUSED` (409) عند اختلافها، و`"fresh"` عند الجدّة.
4. الطازج: تذكُّر المفتاح ثمّ التسجيل → 201. الإعادة: قراءة الملف القائم → 200.

**نتيجة مُعلَنة:** التذكّر والإنشاء في معاملة واحدة، فلا يبقى مفتاح متذكَّر بلا ملفّ عند الفشل. ولو بقي (مخزن سابق) فالمسار يسجّل من جديد بدل أن يعيد 200 عن ملفّ غير موجود.

**البديل المرفوض:** إضافة `idempotencyKey` إلى `registerDriver`. كان سيغيّر توقيعاً يستدعيه كلّ متصل وكلّ اختبار، مقابل وعد لا يوجد إلّا عند حدّ HTTP.

مفتاحان مختلفان للمعرّف نفسه ليسا تعارض مفتاح: الثاني يصل إلى المجال فيرفع `DRIVER_ALREADY_EXISTS` (409). وترتيب مفاتيح JSON لا يصنع «حمولة مختلفة»، لأنّ البصمة تُرتّب قبل الهضم.

### 3.2 المركبات والوثائق: عيب وُجد وصُحِّح

التنفيذ الأول قرأ سجلّ المفتاح عبر `findByIdempotencyKey` و**أعاد السطر الموجود مباشرة**. أثره: مفتاح مُعاد بحمولة **مختلفة** كان يجيب 200 عن مركبة ليست المطلوبة، بدل 409. الآن اللمس الوحيد للسجلّ هو حساب `existed` (رمز الحالة 201 أو 200)، ثمّ **يُستدعى `registerVehicle` / `submitDocument` دائماً** ويبقى قرار الإعادة أو التعارض للمجال حيث كُتب واختُبر.

## 4. القراءات: 404 صريح لا قائمة فارغة

`listDriverZones` و`listDriverVehicles` و`listDriverDocuments` كلّها تتحقق من وجود الملفّ أولاً وترفع `driverNotFound()`. السبب: المستودعات ترجع `[]` للمعرّف المجهول، فلو مرّرناها لأجاب المسار 200 بقائمة فارغة عن سائق لا وجود له، وهذا يخبر المتصل بأنّ السائق موجود وبلا مركبات — وهو أسوأ من الخطأ الصريح.

`GET /eligibility` كذلك: `readEligibility` **يُغلق فاشلاً** ويعيد `unknown` للسائق المجهول، وهو الصواب داخل المجال وخطأ على السلك. المسار يفحص الوجود ويرفع 404، ويثبت اختبار أنّه لا يسجّل سطر أهليّة لسائق مجهول ولا يُظهر كلمة `unknown`. وهذا المسار يستعمل `runner.write` لا `read` لأنّه **يعيد الحساب** ويكتب سطر السجلّ (ADR-012 · «الأهليّة مشتقّة لا مخزّنة»).

القراءة تُظهر الوثائق كلّها بما فيها المستبدلة: تاريخ الأوراق هو ما يجيب لاحقاً عن سبب قرار.

## 5. قواعد الترويسات والأجسام

| الترويسة          | الحال                                  | الحدود                             | عند الخطأ                              |
| ----------------- | -------------------------------------- | ---------------------------------- | -------------------------------------- |
| `Idempotency-Key` | إلزامية في الكتابات كلّها ومنها النبضة  | 8–128 محرفاً؛ قيمة مفردة بلا فاصلة | `400 DRIVER_IDEMPOTENCY_KEY_REQUIRED` عند الغياب · `400 DRIVER_VALIDATION_FAILED` عند الشكل |
| `x-request-id`    | اختيارية                               | ≤ 128 محرفاً؛ قيمة مفردة بلا فاصلة | `400 DRIVER_VALIDATION_FAILED`         |

- الرأس المفقود له رمزه الخاص لا الرمز العام: العقد يملك `DRIVER_IDEMPOTENCY_KEY_REQUIRED`، وإجابته بـ`VALIDATION_FAILED` تُخفي السبب الذي أعلنّاه.
- `requestIdHeader: "x-request-id"` يجعل `request.id` هو `trace_id` في كلّ ردّ خطأ، فمعرّف واحد يربط سجلّ المتصل بسجلّنا.
- الرأس المكرَّر مرفوض مصفوفةً أو نصّاً بفاصلة، لأنّ Node قد يدمج التكرار في نص واحد.
- **لا صدى للمرفوض:** لا رسالة خطأ تُعيد قيمة المعرّف أو المفتاح المرفوضة، وإلّا صار السجلّ مخزناً لكلّ ما كتبه متصل في حقل.
- `PATCH /drivers/{id}` يُبنى مفتاحاً بمفتاح بـ`"key" in body`: **الحقل الغائب ليس الحقل الصريح بقيمة فارغة**. `{"work_city_zone_id": null}` إلغاء منطقة، وغيابه «لا تلمسها».
- الإعادة (`reinstate`) والنبضة لا تقبلان جسماً غير فارغ؛ قبوله وعد بمعامل لا نقرؤه.

## 6. `/health`

```json
{
  "status": "degraded",
  "persistence": "memory",
  "last_tick_at": null
}
```

`ok` عندما يركّب الجذر `persistence: "postgres"`، وإلّا `degraded`. **لا مفتاح `service`** — عقد السائقين لا يعلنه، بخلاف عقد التوزيع؛ وإضافته هنا انحراف صامت. `last_tick_at` كائن حالة حقني يبدأ `null` ولا يتغيّر إلّا بعد نبضة ناجحة، وهو **في الذاكرة بقصد**: مؤشّر تشغيلي لهذه العملية لا حقيقة مشتركة، وترقيته إلى جدول يجعله كذبة عند تشغيل نسختين.

## 7. النبضة

`POST /drivers/eligibility/tick` هو الموضع الوحيد الذي يتحرك فيه الزمن (ADR-012 · القرار 5: «الزمن نبضة لا مؤقّت»). يطلب `Idempotency-Key` ويتحقق منه، و**لا يخزّنه ولا يستعمله لمنع تكرار**: منع الأثر المكرّر بنيوي — إعادة الحساب لا تجد ما تغيّره بعد نبضة ناجحة — وتخزين مدخلة لكل نبضة ينمو بلا حدّ. البديل (إسقاط الرأس من العقد) مرفوض: العقد يطلبه على كلّ كتابة. ويثبت اختبار أنّ سجلّ المفتاح يبقى `null` بعد نبضة.

النبضة **لا تمرّر `traceId`**: طلب واحد قد يعيد حساب مئات السائقين، ووسم كلّ أسطرهم بمعرّف طلب واحد يفسد التدقيق بدل أن يخدمه.

## 8. خريطة الأخطاء (21 رمزاً)

الغلاف **متداخل**: `{ "error": { "code", "message", "details"? }, "trace_id" }` — وهو شكل عقد السائقين، بخلاف الغلاف المسطَّح في التوزيع. الحالة تأتي من صنف الرمز في `@wasla/contracts-driver` (`DRIVER_ERROR_CODE_CLASS`)، فلا رقم HTTP مكتوب بيد في معالج.

| الصنف                 | HTTP | الرموز                                                                                                                  |
| --------------------- | ---: | ----------------------------------------------------------------------------------------------------------------------- |
| `validation_error`    |  400 | `VALIDATION_FAILED` · `IDEMPOTENCY_KEY_REQUIRED` · `VEHICLE_CLASS_UNKNOWN` · `SERVICE_KIND_UNKNOWN` · `DOCUMENT_TYPE_UNKNOWN` |
| `not_found`           |  404 | `NOT_FOUND` · `VEHICLE_NOT_FOUND` · `DOCUMENT_NOT_FOUND`                                                                 |
| `conflict`            |  409 | `IDEMPOTENCY_KEY_REUSED` · `ALREADY_EXISTS` · `DOCUMENT_ALREADY_REVIEWED` · `SUSPENDED` · `NOT_SUSPENDED`                |
| `unprocessable`       |  422 | `ZONE_UNKNOWN` · `PRIMARY_VEHICLE_REQUIRED` · `VEHICLE_RETIRED` · `DOCUMENT_EXPIRY_INVALID` · `POLICY_NOT_FOUND` · `POLICY_NOT_FROZEN` |
| `bad_gateway`         |  502 | `CANDIDACY_PUBLISH_FAILED`                                                                                              |
| `service_unavailable` |  503 | `UNAVAILABLE`                                                                                                           |

- خطأ Fastify بحالة 400 أو 415 (جسم مشوَّه أو نوع محتوى خاطئ) → `400 DRIVER_VALIDATION_FAILED`.
- كلّ ما عدا ذلك غير مصنَّف → **`503 DRIVER_UNAVAILABLE` لا 500**: ما يعطب هنا تخزين أو دليل مناطق أو صندوق صادر، و`503` تخبر المتصل بأنّ الإعادة قد تنجح. ورسالة الخطأ الداخلية لا تُسرَّب إلى الجسم.
- مسار Fastify المجهول يبقى 404 بشكله الافتراضي؛ إجابته بـ`DRIVER_NOT_FOUND` تخبر متصلاً أخطأ في كتابة المسار بأنّ **السائق** مفقود.
- `DRIVER_CANDIDACY_PUBLISH_FAILED` (502) **غير قابل للحدوث في MR 4/6**: `publishCandidacy` يسجّل الفشل ويترك الكتابة المحلية قائمة ولا يرفع. الربط منفَّذ ومُبرهَن باختبار يحقن Runner يرفعه، فيبقى على MR 5/6 قرار موضع الرفع وحده.

## 11. ماذا بعد

- **MR 5/6:** `HttpCandidacyPort` إلى المطابقة (8088)، ودليل مناطق عبر HTTP يُلغي الانحرافين 6 و7، وواجهة `driver-bot`. وهو الموضع الذي يصير فيه 502 قابلاً للحدوث فعلاً.

- تبقى قرارات [ADR-012](../15-decisions/ADR-012-driver-core-eligibility-derivation-and-candidacy-publication.md) غير قابلة للتفاوض: الأهليّة مشتقّة، ولا كتابة في قاعدة المطابقة، والسائق يعلن `available|offline` وحدهما، والزمن نبضة.
