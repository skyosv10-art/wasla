## 1. A defect found before activation (fixed in CLM-0448)

ADR-060 says observe "verifies and logs, never rejects". That held for the
assertion itself (`applyUserAssertion` never denies in observe), but it did **not**
hold for ownership. In observe, a **valid** assertion sets `request.endUser`, and the
receivers' ownership helpers then threw 404 on a mismatch, exactly as in enforce:

| Service | Checks that rejected in observe before the fix |
|---|---|
| negotiations | `opened_by`, `proposed_by`, `acting_party`, `author_role`, `thread_membership`, `list_filter` |
| matching | `driver_public_id` |
| marketplace | `store_owner`, `owner_filter`, `inventory_membership` |

Turning observe on with that code would have rejected production requests, which the
owner forbade. The fix is one shared decision point,
`endUserOwnershipDenied(request, matches, check)` in `@wasla/service-auth/fastify`:

- no `endUser` (off, or no valid assertion) → `false`, no check, no log;
- match → `false`;
- mismatch in **enforce** → `true` (the caller answers 404, unchanged);
- mismatch in **observe** → `false`, plus one `warn` line
  `{event: "user_assertion_ownership", outcome: "would_reject", mode, check, route, caller, act}`
  (no public id, no assertion).

Tests (they fail against the old behaviour; checked with a mutation run):
`packages/service-auth/src/__tests__/user-assertion.test.ts` (observe/enforce/off on a
synthetic owned route), negotiations `opened_by` mismatch → 201 and non-party read →
200 in observe, matching `PUT /candidacy` mismatch → 200 in observe, marketplace
store owner, owner filter and inventory non-member → 2xx in observe. The enforce tests
are unchanged and still pass.

Every service now also logs one boot line, `user_assertion_config` (audience, mode,
kid list) and, in identity, `user_assertion_signer` (enabled, kid). Key material is
never logged. That makes the activation checkable from the logs alone.

## 2. Activation plan (executed only after CLM-0448 is merged and deployed)

| Step | Service(s) | Variable | Value |
|---|---|---|---|
| 1 | `wasla-identity` | `WASLA_USER_ASSERTION_SIGNING_KEY` | `<kid>:<base64 PKCS#8>` (secret) |
| 2 | `wasla-negotiations`, `wasla-matching`, `wasla-marketplace` | `WASLA_USER_ASSERTION_PUBLIC_KEYS` | `{"<kid>":"<base64 SPKI>"}` |
| 3 | same three | `WASLA_USER_ASSERTION_MODE` | `observe` |
| 4 | the four above | — | redeploy pinned to the commit already live (no code drift) |

- The key pair is generated by the operator (owner's delegate) with `umask 077`, set
  through the Render API, then destroyed with `shred -u`. It is never written to the
  repository, to CI or to a log. Render is the only store (lifecycle §3). If the owner
  prefers a pair generated on their own machine, rotation is lifecycle §5 and costs no
  downtime.
- Nothing else changes: no other variable and no other service. The diff
  `scripts/ops/render-env-fingerprint.py diff t0 t1` must list exactly these 7 keys.
- **Rollback** (any time, no data effect): delete the three variable names from the
  four services (or set `WASLA_USER_ASSERTION_MODE=off`), redeploy. With the mode
  unset, the receivers return to `off`, the code path from before activation.
- **Never** `enforce` in this phase.

## 3. Measurement

`scripts/ops/risk-0042/observe-report.py` reads the Render logs of the four services
over a window and aggregates `user_assertion_outcome` (valid / invalid + reason),
`user_assertion_ownership` (would_reject + check), `user_assertion_issued` and
non-health traffic per route. Its output lists which operations **would fail under
enforce**, and why.

Baseline measured before activation (24 h, 2026-10-02T09:45Z → 2026-10-03T09:45Z):
non-health traffic on the four services is only uptime pings (`GET /` and `HEAD /`,
12 each). **No end-user request reached any asserted route.** So an observe window
without traffic proves the configuration, not enforce readiness. The report says so
instead of reading silence as "no failures".

## 4. What this document does not claim

- It does not claim RISK-0042 is mitigated or closed.
- It does not claim enforce readiness. That needs real (or an approved synthetic)
  end-user traffic on each asserted route with zero `invalid` and zero `would_reject`.
- It does not change ADR-060, ADR-052 or ADR-058.
