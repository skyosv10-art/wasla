## 5. الحدُّ المُعلَنُ (تصحيحٌ بعدَ المراجعةِ المستقّلةِ)

النمطُ يقيسُ **الإشارةَ المباشرةَ للاسمِ fetch** في مواضعِ القيمةِ والنداءِ. ما لا يُثبِتُهُ:

- ملفٌّ يصلُ إلى fetch عبر ربطٍ لا يذكرُ الاسمَ فيهِ إطلاقًا — مثالٌ عبر ملفينِ: `deps.ts` يصدِّرُ `export const t: Transport = (i: string) => Promise.resolve({} as Response)` (لا ذكرَ لـfetch)، والمستهلِكُ يستقبلُ `t` منفذًا. الربطُ بنفسِ الاسمِ في ملفٍّ واحدٍ (`const a = fetch; const b = a;`) **يُحصى** لأنّ سطرَ الإسنادِ الأولِ يذكرُ fetch — تحتاجُ الحالةُ الأولى تحليلَ تدفقِ بياناتٍ (AST) — **لا يُدَّعى بعدُ**.
- النمطُ لا يستبعدُ التعليقاتِ: أنماطُ مواضعِ القيمةِ ضُبِطت على الشجرةِ لتفادي الإنذاراتِ الكاذبةِ على التعليقاتِ المعروفةِ، وذكرٌ في تعليقٍ يطابقُ النمطَ **يُحصى** (اتجاهُ الفشلِ المغلقِ لا ثغرةً).
- (إضافةٌ مؤرَّخةٌ 2026-10-21) هذا السلوكُ صارَ مُثبَّتاً بحالةِ حوكمةٍ صريحةٍ «ذكرُ fetch( في تعليقٍ وحدَهُ يُحصى ويُسقِط بلا استثناءٍ» وبقياسٍ معزولٍ ثلاثيٍّ في [raw/comment-only-isolation.txt](raw/comment-only-isolation.txt) (أساسٌ 0 · تعليقٌ بـfetch( 1 · تعليقٌ بلاها 0). وصفُ PR #801 الأصليُّ ادّعى العكسَ وصُحِّحَ.
- (إضافةٌ مؤرَّخةٌ 2026-10-21) الاستثناءُ لا يحلُّ محلَّ إثباتِ التوقيعِ: طفرةُ حذفِ التوقيعِ قُتِلت محلّياً في المساراتِ الداخليّةِ الثلاثةِ — user-assertion 1/5 · identity-bootstrap 1/8 · tick-scheduler/http-tick 1/15 (الإخفاقُ بعدَ الحذفِ، الأساسُ أخضرُ) — [raw/signature-removal-mutations.txt](raw/signature-removal-mutations.txt). قياسٌ محلّيٌّ لا CI؛ bot-api-client.ts حدٌّ خارجيٌّ إلى Telegram بلا توقيعِ خدمةٍ بالتصميمِ فليسَ ضمنَها.
- الاستثناءُ المُعلَنُ للاتصالِ الداخليِّ توثيقٌ وتصنيفٌ، **لا بديلٌ عن إثباتِ التوقيعِ** — إثباتُ توقيعِ `user-assertion` و`identity-bootstrap` يعيشُ في اختباراتِ التكاملِ (تشغّلها CI على PostgreSQL حقيقيٍّ) وتُوثَّقُ حالتُها هنا كذلك.
