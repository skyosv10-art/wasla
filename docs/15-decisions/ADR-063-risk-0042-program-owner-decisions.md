# ADR-063 — سجلّ قرارات Program Owner لفجوات RISK-0042 الـ19

| | |
|---|---|
| **الحالة** | Proposed — قرارات معلَّقة تسجيلًا لا تنفيذًا. لا تُفتح Claims تنفيذية حتى اعتماد كل قرار |
| **التاريخ** | 2026-10-05 |
| **عنصر العمل** | `M0-49` (RISK-0042) |
| **المرجع** | [ADR-062](ADR-062-risk-0042-architectural-execution-plan.md) — الخريطة المعمارية |
| **لا يغيّر** | Production · Render · migrations · cutover · observe/enforce. لا Claims تنفيذية. RISK-0042 يبقى `open` |

---

## 1. السياق

أنتجت ADR-062 خريطة تنفيذ معمارية كاملة للفجوات الـ19 المتبقية في RISK-0042. الخريطة صنّفت الفجوات إلى أربعة أصناف (A/B/C/D) وحدّدت لكل فجوة: endpoint، الخدمة المالكة، الخطورة، user-bound vs system-bound، caller الإنتاجي الحالي والمطلوب، مصدر الهوية، ملاءمة OBO، البديل، مالك القرار، معيار القبول، التبعيات، الاختبارات، migration/rollback، Claim المقترح، والمخرج المقترح.

هذه الوثيقة **تسجّل قرارات Program Owner المطلوبة** لكل فجوة أو مجموعة فجوات، مع الخيارات المتاحة، التبعات، والمخاطر. **لا تُفتح Claims تنفيذية.** الهدف هو توثيق ما يحتاجه صاحب القرار من معلومات لاتخاذ قرار مكتوب.

## 2. قرارات Program Owner المعلَّقة

### PO-001 — اعتماد نطاق التنفيذ (الفجوات الـ13 من صنف A)

| | |
|---|---|
| **الفجوات** | D1, D2, D3, D4, D6, G1, G2, G3, S1, S2, S3, S4, U1 |
| **القرار** | هل تُغلق الفجوات الـ13 (صنف A) في دفعات P2 متتابعة، أم دفعة واحدة؟ |
| **الخيار 1** | دفعات متتابعة بترتيب الخدمات: delivery → geography → support → subscriptions. كل دفعة claim مستقل + PR مستقل + CI + CODEOWNER review. الميزة: مراجعة أصغر، عزل الأخطاء. الكلفة: 4 دورات دمج |
| **الخيار 2** | دفعة واحدة لكل الفجوات الـ13. claim واحد + PR واحد. الميزة: دورة واحدة. الكلفة: مراجعة كبيرة، صعوبة العزل |
| **الخيار 3** | دفعات حسب الأولوية: high أولاً (D1, D3, G1, G2, G3)، ثم medium (D2, D4, D6, S1-S4)، ثم low (U1). الميزة: إغلاق الأعلى تأثيرًا أولاً. الكلفة: 3 دورات |
| **التبعات** | كل الخيارات تحتاج بناء تدفقات caller إنتاجي: customer-bot → delivery/geography/support، partner-bot → delivery، driver-bot → geography. هذه تدفقات جديدة لم تُبنَ بعد |
| **مخاطر التأجيل** | الفجوات الـ13 بلا منادي إنتاجي اليوم، فلا مسار هجوم حي. لكن البيانات حساسة (موقع، طلبات، تذاكر) وتأجيل الإغلاق يطيل نافذة الخطر متى وُجد caller |
| **مخرج مقترح** | الخيار 3 (دفعات حسب الأولوية) |

### PO-002 — قرار audit: حقول الفاعل في جسم الطلب (A1)

| | |
|---|---|
| **الفجوة** | A1 — `POST /audit/events` يقبل `actor_id`/`actor_role` من الجسم ويكتبهما في سجل التدقيق بلا تحقق |
| **القرار** | هل يُزيل `actor_id`/`actor_role` من عقد `POST /audit/events` ويُشتقّان من `serviceCaller.onBehalfOfPublicId` أو من تأكيد المستخدم؟ |
| **الخيار 1** | إزالة الحقول من العقد واشتقاقها من الرمز فقط. الميزة: لا انتحال ممكن. الكلفة: تغيير عقد منشور، كسر callers قائمين (لا يوجد منادي إنتاجي اليوم، فلا كسر فعلي) |
| **الخيار 2** | إبقاء الحقول كقرار تصميم: audit سلطة إدارية، والمنادي موقَّع بصلاحية. الميزة: لا تغيير عقد. الكلفة: الفجوة تبقى مفتوحة بقرار مقبول |
| **الخيار 3** | قبول تأكيد مستخدم إن كان الفاعل مستخدمًا، واشتقاق من الرمز إن كان نظاميًا. الميزة: دقة. الكلفة: مساران منفصلان أو منطق تفرع |
| **التبعات** | تغيير العقد (الخيار 1) يحتاج تحديث `services/audit/contracts/` و`api-types.ts` المولَّد |
| **مخاطر التأجيل** | audit هو وجهة السجل، لا مصدر للحقائق. الخطر منخفض لكنه قابل للاستغلال لتزوير سجل التدقيق |
| **مخرج مقترح** | الخيار 1 (إزالة الحقول واشتقاقها من الرمز) |

### PO-003 — قرار reputation: مسارات مُرشَّحة بشخص (R1, R2)

| | |
|---|---|
| **الفجوات** | R1 — `GET /reputation/facts`، R2 — `GET /reputation/ratings` — كلاهما `internalScoped` بمُرشِّح شخص (`subject_public_id`، `raterPublicId`) بلا مقارنة |
| **القرار** | هل reputation يقبل تأكيد مستخدم على المسارات المُرشَّحة بشخص، أم يبقى نظاميًا بقرار تصميم؟ |
| **الخيار 1** | قبول تأكيد مستخدم: المسار المُرشَّح بـ`subject_public_id` يجب أن يطابق `endUser.publicId`. الميزة: إغلاق الفجوة. الكلفة: إضافة `asserted()` + مقارنة + اختبارات |
| **الخيار 2** | تقسيم المسار: قراءة نظامية بصلاحية مستقلة + مسار مُرشَّح بـ`asserted`. الميزة: فصل التشغيل عن المستخدم. الكلفة: مساران |
| **الخيار 3** | إبقاء `none` بقرار تصميم: reputation بيانات تشغيلية داخلية، والمُرشِّح لا يكشف أكثر مما يعرف المنادي. الميزة: لا تغيير. الكلفة: الفجوة تبقى مفتوحة بقرار مقبول |
| **التبعات** | الخيار 1 و2 يحتاجان تدفّق caller إنتاجي إلى reputation (لا يوجد اليوم) |
| **مخاطر التأجيل** | البيانات تشغيلية بطبيعتها، والخطر منخفض. لكن `subject_public_id` يُسمّي شخصًا — فكل حامل صلاحية يقرأ وقائع/تقييمات أي شخص |
| **مخرج مقترح** | الخيار 3 (إبقاء `none` بقرار تصميم) — البيانات تشغيلية، والمُرشِّح لا يكشف نمطًا حساسًا |

### PO-004 — قرار billing: فجوات كامنة (B1, B2)

| | |
|---|---|
| **الفجوات** | B1 — `GET /billing/invoices` (ترشيح بـ`store_public_id`)، B2 — `GET /billing/invoices/:id` — كامنتان: لا caller إنتاجي من المتجر اليوم |
| **القرار** | هل تُبنى مسارات partner-bot إلى billing الآن، أم تُؤجَّل الفجوتان الكامنتان حتى يُعرَض billing للمتجر؟ |
| **الخيار 1** | بناء partner-bot → billing flow الآن وإغلاق الفجوتين بـ`asserted`. الميزة: إغلاق فوري. الكلفة: بناء caller إنتاجي جديد + تكامل partner-bot مع billing |
| **الخيار 2** | تأجيل الفجوتين بقرار: لا caller إنتاجي اليوم = لا خطر حي. الميزة: لا عمل الآن. الكلفة: الفجوتان تبقيان مفتوحتين بقرار مقبول حتى يُعرَض billing للمتجر |
| **التبعات** | الخيار 1 يحتاج إضافة `billing` إلى `ASSERTION_AUDIENCES_BY_ACTOR` لـ`store_staff`، وتفعيل `userAssertionConfigFromEnv` على billing |
| **مخاطر التأجيل** | منخفضة — الفجوتان كامنتان بلا caller إنتاجي. لكن متى عُرِض billing للمتجر، تصبح الفجوة حية فورًا بلا إغلاق مسبق |
| **مخرج مقترح** | الخيار 2 (تأجيل بقرار) — الكلفة أعلى من الفائدة اليوم |

### PO-005 — قرار fulfillment-transition: مسار مركب (D5)

| | |
|---|---|
| **الفجوة** | D5 — `POST /store-orders/:orderPublicId/fulfillment-transition` — انتقال التنفيذ يحتاج هوية المتجر + السائق معًا |
| **القرار** | هل يُقسم المسار إلى متجر مؤكد + سائق مؤكد منفصلين، أم يُبنى حدث مركب؟ |
| **الخيار 1** | تقسيم المسار: مسار متجر بـ`asserted` (store_staff) + مسار سائق بـ`asserted` (driver). الميزة: كل مسار لهوية واحدة واضحة. الكلفة: تغيير عقد (مساران بدلاً من واحد) |
| **الخيار 2** | حدث مركب: المسار يقبل تأكيدين (store_staff + driver) في طلب واحد. الميزة: عقد واحد. الكلفة: منطق تفرع في المعالج، تأكيد مزدوج |
| **الخيار 3** | إبقاء `none` بقرار: انتقال التنفيذ سلطة نظامية (dispatch/delivery). الميزة: لا تغيير. الكلفة: الفجوة تبقى مفتوحة |
| **التبعات** | الخيار 1 و2 يحتاجان تدفّق caller إنتاجي إلى delivery (customer-bot/partner-bot/dispatch) |
| **مخاطر التأجيل** | متوسط — انتقال التنفيذ يغيّر حالة الطلب، والفجوة تسمح بانتقال باسم أي متجر/سائق |
| **مخرج مقترح** | الخيار 1 (تقسيم المسار) — هوية واحدة لكل مسار أوضح من حدث مركب |

### PO-006 — تفعيل P3 (observe/enforce على Render)

| | |
|---|---|
| **النطاق** | كل خدمة فيها مسار `asserted` (بعد إغلاق الفجوات الـ13 من صنف A) |
| **القرار** | متى وكيف يُفعَّل `WASLA_USER_ASSERTION_MODE` على Render لكل خدمة؟ |
| **الخيار 1** | تفعيل تدريجي: `observe` أولاً لكل خدمة (مراقبة بلا رفض)، ثم `enforce` بعد التحقق من 0 رفض غير متوقع. الميزة: كشف قبل الرفض. الكلفة: نافذة observe لكل خدمة |
| **الخيار 2** | تفعيل مباشر: `enforce` فور إغلاق الفجوات. الميزة: إغلاق فوري. الكلفة: رفض غير متوقع ممكن |
| **الخيار 3** | تأجيل P3 حتى اكتمال كل P2 (الفجوات الـ13). الميزة: لا تفعيل ناقص. الكلفة: RISK-0042 يبقى `open` حتى P3 |
| **التبعات** | تفعيل P3 هو تغيير على Production/Render — يحتاج قرارًا مكتوبًا من Program Owner لكل خدمة |
| **مخاطر التأجيل** | RISK-0042 لا يُغلق إلا بعد P3. التأجيل يطيل فترة `open` لكنه آمن (الوضع `off` لا يغيّر سلوك الإنتاج) |
| **مخرج مقترح** | الخيار 1 (تفعيل تدريجي observe ثم enforce) لكل خدمة بعد إغلاق فجواتها |

## 4. معايير إغلاق RISK-0042 بالكامل (مُحدَّثة)

1. كل قرار من PO-001 إلى PO-006 يُتَّخذ بقرار مكتوب من مالكه
2. الفجوات الـ13 (صنف A) تُغلق بـ`asserted()` + اختبارات (عند اعتماد PO-001)
3. الفجوة A1 تُغلق أو تُقبَل بقرار تصميم (عند اعتماد PO-002)
4. الفجوتان B1, B2 تُؤجَّلان أو تُغلقان (عند اعتماد PO-004)
5. الفجوة D5 تُغلق أو تُؤجَّل (عند اعتماد PO-005)
6. الفجوتان R1, R2 تُغلقان أو تُقبَلان بقرار تصميم (عند اعتماد PO-003)
7. P3 يُفعَّل لكل خدمة (عند اعتماد PO-006)
8. اختبار هجوم حي: بوت مخترق لا يستطيع الوصول إلى موارد مستخدم آخر
9. مراجعة Security Owner وتأكيد عدم وجود مسار هجوم جديد
10. تحديث `RISK_REGISTER.md`: RISK-0042 → `closed` أو `accepted`

RISK-0042 يبقى `open` حتى تتحقق كل المعايير. هذه الوثيقة تسجّل القرارات ولا تنفذها.
