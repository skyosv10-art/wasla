# بروتوكول تشغيل خارطة الطريق الرئيسية والتوثيق مع كل دفع

**يقرأه كل مساهم قبل أول تعديل، ويطبقه كل وكيل آلي قبل إنشاء commit أو Merge Request.** هذا البروتوكول يحول الخارطة من ملف وصفي إلى نظام تشغيل للعمل.

## 1. قاعدة العمل الأساسية

كل عمل ذو معنى = Work Item موجود في `LAUNCH_EXECUTION_BOARD.md` + إدخال في `TASK_LOG.md` + دليل تقني مناسب، وفق تعريفات الخارطة الرئيسية. لا يملك أحد حق كتابة كود “صغير” خارج هذا النظام. التعديل الصغير قد يغير API أو أماناً أو سلوكاً تشغيلياً؛ لهذا لا توجد فئة “لا تحتاج توثيقاً”.

لا يعد التعديل ذا معنى فقط عندما يكون محصوراً في تصحيح typo داخل الملف نفسه، أو إعادة تنسيق لا تغير المحتوى. في حال الشك، تعامل معه كتعديل ذي معنى ووثقه.

## 2. قبل البدء — بوابة Ready

نفذ بالترتيب التالي:

0. **ابحث قبل كل شيء (إلزامي):** `bash scripts/checks/find-existing-work.sh "<المجال أو المسار>"`، وراجع [`WORK_INDEX.md`](WORK_INDEX.md). إن وجدت عملاً مطابقاً أو حجزاً نشطاً فلا تنشئ عملاً موازياً؛ نسّق مع مالكه أو أنشئ عنصراً تابعاً يشير إليه.
1. اقرأ `LAUNCH_TO_100_ROADMAP.md` (مصدر الحقيقة الوحيد) و`LAUNCH_EXECUTION_BOARD.md` و`TASK_LOG.md` الحديث.
2. اختر عنصراً موجوداً؛ إذا لم يوجد، أنشئه في اللوحة بحالة `Not Started` مع سبب ومالك وتبعيات ومعيار قبول قبل كتابة الكود.
3. لا تبدأ عنصراً تابعاً إذا كان اعتماده `Blocked` أو غير `Completed`.
4. عيّن Primary وSecondary Owner. إذا لم يوجد مالك، تبقى الحالة `Blocked` ولا يبدأ العمل.
5. **احجز النطاق (إلزامي قبل أول commit):** أضف سطراً في [`WORK_CLAIMS.md`](WORK_CLAIMS.md) بمعرّف حجز ومالك وفرع و**مسارات نطاق محددة** وتاريخ انتهاء. لا يمر الدفع بدونه، ولا يمر إن تقاطع نطاقك مع حجز نشط لغيرك.
6. حدّث الصف إلى `In Progress`، ثم أضف إدخال بدء في `TASK_LOG.md` يربط العنصر والفرع والهدف.
7. تأكد أن Definition of Ready مكتملة: نطاق، غير نطاق، عقود، مخاطر، اختبارات، migrations، config، deploy، rollback، وقرار ADR إن لزم.

## 3. مع كل دفع — المعاملة التوثيقية الواحدة

قبل الدفع، يجب أن يحتوي نفس النطاق على الثلاثة التالية:

| السجل | الحد الأدنى الإلزامي |
|---|---|
| `TASK_LOG.md` | إدخال جديد يجيب عن ماذا/لماذا/أين/اختبارات/مخاطر/ما بقي/الخطوة التالية وروابط MR/ADR. |
| `LAUNCH_EXECUTION_BOARD.md` | تحديث الصف: الحالة، الدليل، العائق أو الخطوة التالية، وتاريخ آخر تحقق إذا تغيرت الحالة. |
| وثيقة المجال | عقد/API/Event/schema/runbook/ADR عند تغير الحقيقة التي تصفها. |

استعمل القالب أدناه. يجب أن يذكر `Work Item(s):` معرفاً واحداً على الأقل موجوداً في اللوحة. لا تكتب “عدة تحسينات” من دون معرفات.

```md
## [YYYY-MM-DD] — <عنوان قصير>

- **Work Item(s):** Mx-yy
- **Status:** In Progress | Ready for Gate | Blocked | Completed
- **What / Why:** ماذا تغير ولماذا الآن؟
- **Changed:** المسارات والخدمات والعقود/الأحداث/الجداول المتأثرة.
- **Verification:** الأوامر، البيئة، والنتيجة الفعلية.
- **Security / Data / Deployment:** الأثر أو "لا أثر" مع سبب.
- **Known Issue / Blocker:** العائق ومالكه وتاريخ المراجعة، أو "لا يوجد".
- **Evidence:** MR/commit/artifact/runbook/ADR.
- **Next:** الخطوة الذرية التالية والمالك.
- **Primary / Secondary:** الأسماء أو الفرق.
```

## 4. الانتقال بين الحالات

| من | إلى | الشرط |
|---|---|---|
| Not Started | In Progress | Ready مكتملة، مالكان معيّنان، سجل بدء موجود. |
| In Progress | Ready for Gate | الكود/الوثائق/الاختبارات المحلية مكتملة والدليل مرفق. |
| Ready for Gate | Completed | CI الإلزامية والـExit Gate ومراجعة Secondary Owner نجحت. |
| أي حالة | Blocked | يكتب السبب، الأثر، المالك، تاريخ المراجعة، والبديل. |
| Blocked | In Progress | الدليل يثبت إزالة العائق؛ لا تكتف بالوعد. |
| Completed | أي حالة | لا يعاد الفتح إلا بعيب/طلب تغيير جديد، مع عنصر جديد أو ADR. |

## 5. ما الذي يغير أي مستند؟

| نوع التغيير | اللوحة | سجل العمل | وثائق إضافية |
|---|---|---|---|
| إصلاح bug | نعم | نعم | تقرير bug/اختبار regression. |
| API أو Event | نعم | نعم | OpenAPI/events/errors/contracts وconsumer impact. |
| Schema/Migration | نعم | نعم | schema، migration، rollout/restore runbook. |
| Security/IAM/secret | نعم | نعم | threat model/policy/rotation evidence. |
| UI أو رحلة مستخدم | نعم | نعم | spec، acceptance، accessibility/E2E evidence. |
| Infra/CI/config | نعم | نعم | IaC/env/runbook/rollback. |
| ترتيب milestone أو نطاق | نعم | نعم | ADR + `ROADMAP.md` + هذه الخارطة. |
| توثيق أو typo فقط | عند أثر حالة/قرار | عند تغيير حقيقة | لا يلزم غيره إذا لم تتغير الحقيقة. |

## 6. الإلزام الآلي

المدخل الموحّد واحد لا أكثر:

```bash
bash scripts/checks/verify-governance.sh    # أو: pnpm run governance:verify
```

يشغّل بالترتيب، ويرفض ما يلي:

| الفحص | يرفض |
|---|---|
| `validate-launch-board.sh` | بنية لوحة معطوبة، حالة غير معتمدة، ID مكرر، صف `Completed` بدليل فارغ. |
| `validate-work-claims.sh` | حجز مزدوج لنفس العنصر، **تقاطع نطاقات بين جهتين**، تعديل ملف خارج النطاق المحجوز، حجز منتهٍ أو فرع لا يطابق. |
| `require-doc-update.sh` | تغيير ذو معنى بلا تحديث `TASK_LOG.md` و`LAUNCH_EXECUTION_BOARD.md` معاً، وإدخالاً بلا `**Work Item(s):**`. |
| `scan-secrets.sh` | دخول أسرار إلى الشجرة. |

ويعمل في ثلاث طبقات: `scripts/hooks/pre-push` محلياً، ووظيفة `governance-guard` و`doc-coverage` في `.gitlab-ci.yml`، ومراجعة `CODEOWNERS`.

هذا الإلزام يغطي Merge Requests خادمياً، ويعمل hook محلياً كتنبيه مبكر. **حده المعروف:** لا يمكن لسكربت داخل المستودع أن يمنع دفعاً مباشراً على الخادم إذا سمحت إعدادات GitLab به. لذلك يجب حماية `main`، منع direct push، فرض pipeline الناجح، وفرض approval من CODEOWNERS على مسارات التقدم. إذا احتاجت المؤسسة منع كل push branch من دون استثناء، يفعل مسؤول GitLab server-side push rule أو pre-receive policy؛ لا تدّع هذه الوثائق أنها توفر صلاحية إدارية لا يملكها المستودع.

## 7. بروتوكول الدمج والإصدار

لا يدمج MR إلا إذا: العنصر موجود، اللوحة والسجل محدثان، tests وsecurity مناسبة لنوع التغيير ناجحة، reviewer يراجع الدليل لا الوصف فقط، ولا يوجد عائق مخفي. بعد الدمج، يحدّث المالك الدليل برابط commit/pipeline النهائي عند الحاجة. لا ينشأ إصدار من فرع غير محمي أو من pipeline حمراء.

## 8. منع التكرار وحل التعارض بين مساهمين

المنع قبل الحل: لا يعمل مساهمان في نفس النطاق لأن `validate-work-claims.sh` يرفض تقاطع النطاقات من الأساس. وإذا احتاج عملان مساراً مشتركاً فعلاً، يفتح Program Owner قراراً ويقسم العنصر إلى عناصر متسلسلة — **ولا يُعطّل الفحص بحال**.

### 8.1 بعد الدمج — إقفال الدورة (إلزامي)

1. انقل سطر الحجز إلى «الحجوزات المحرَّرة» بحالة `Released` مع رابط الدليل.
2. حدّث حالة العنصر في اللوحة ورابط الـpipeline النهائي.
3. حدّث [`WORK_INDEX.md`](WORK_INDEX.md) إن تغيرت حالة منطقة كود (من `Placeholder` إلى `In Progress` أو `Implemented`).

الحجز الذي لا يُحرّر يقفل النطاق على الآخرين حتى تاريخ انتهائه، وهو خلل تشغيلي يُحاسب عليه المالك.

### 8.2 التعارض في الوثائق

لا يحرر مساهمان الصف نفسه بلا تنسيق. إذا تعارض العمل، يفتح Program Owner قراراً ويقسم العنصر إلى عناصر جديدة بتبعيات واضحة. لا تحل تعارض الوثائق بحذف إدخال الطرف الآخر؛ يحتفظ `TASK_LOG.md` بالسجل الزمني، وتظهر اللوحة القرار الحالي فقط.

## 9. تعليمات الوكلاء الآليين

أي وكيل آلي يجب أن: يقرأ [`README.md`](README.md) وهذه الوثيقة واللوحة، يصرح بعنصر العمل في وصف MR، لا يغير الحالة إلى `Completed` من تلقاء نفسه، يكتب نتائج الأوامر الفعلية لا المتوقعة، ويحدد أي عدم يقين أو فشل. لا يجوز لوكيل أن يفتح أو يوسع نطاقاً جديداً بلا ADR/موافقة حسب القاعدة.

ويُلزم الوكيل زيادةً بما يلي، لأن الوكلاء أكثر من يكرر عملاً موجوداً:

1. **لا يكتب سطراً واحداً** قبل تشغيل `find-existing-work.sh` وقراءة [`WORK_INDEX.md`](WORK_INDEX.md) و[`WORK_CLAIMS.md`](WORK_CLAIMS.md).
2. **يحجز باسم مسؤول بشري** بصيغة `@handle (agent:<name>)` — لا يوجد مالك أداة بلا مسؤول بشري.
3. **لا يلمس ملفاً خارج نطاق حجزه**، ولا يوسّع النطاق بعد بدء الكتابة.
4. **لا ينشئ وثيقة حوكمة جديدة** موازية لما في `docs/16-progress/`. إن رأى نقصاً، يُعدّل الموجود أو يقترح ADR.
5. **يشغّل `verify-governance.sh` ويلصق المخرج الفعلي** في وصف الـMR.
6. **يعلن ما لم يتحقق منه** صراحةً بدلاً من صياغة توحي بالإثبات.
